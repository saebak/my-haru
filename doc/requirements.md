# My Daily Todo 요구사항 명세서

## 1. 문서 정보

- 문서 버전: 0.5.0
- 작성일: 2026-09-08
- 대상 서비스: 앱인토스에서 실행되는 개인용 투두·습관 관리 미니앱
- 최종 목표: 직접 사용할 수 있는 앱을 완성한 뒤 앱인토스에 출시하고 인앱 광고로 수익화한다.
- 기본 기술 방향: React, TypeScript, 최신 앱인토스 WebView SDK

## 2. 제품 목표

### 2.1 핵심 목표

1. 할 일과 반복 습관을 빠르게 등록하고 관리할 수 있어야 한다.
2. 앱을 종료하거나 네트워크가 끊겨도 데이터가 보존되어야 한다.
3. 알림과 달성 기록을 통해 사용자가 계획을 꾸준히 수행하도록 도와야 한다.
4. 개인 사용으로 제품을 검증한 후 로그인과 서버 동기화를 추가해야 한다.
5. 앱인토스의 비게임 앱 검수를 통과하고 인앱 광고 수익을 발생시켜야 한다.

### 2.2 대상 사용자

- 1차 사용자: 개발자 본인
- 출시 후 사용자: 일상 할 일과 반복 습관을 간단하게 관리하려는 토스 사용자

### 2.3 제품 성공 기준

- 사용자가 1분 안에 첫 할 일을 만들고 완료할 수 있다.
- 앱을 다시 실행했을 때 기존 할 일과 달성 기록이 유지된다.
- 매일·매주·특정 요일 반복이 정확하게 동작한다.
- 알림을 누르면 해당 할 일 화면으로 이동한다.
- Android와 iOS의 토스 앱에서 핵심 기능이 정상 동작한다.
- 앱인토스 운영·기능·디자인·보안 검수를 통과한다.
- 운영 광고가 정상 노출되고 광고 성과와 정산 내역을 확인할 수 있다.

## 3. 개발 단계

### 3.1 1단계: 개인 사용 MVP

- 모바일 중심 화면 구성
- 할 일 생성·조회·수정·완료·삭제
- 마감일, 우선순위, 메모
- 선택 날짜의 단일 목록, 완료 항목 하단 배치와 수동 순서 저장
- 캘린더 날짜별 할 일 표시
- 반복 습관과 달성 기록
- 로컬 데이터 저장과 백업·복원
- 핵심 단위·통합 테스트

완료 조건: 로그인과 서버 없이도 한 기기에서 매일 안정적으로 사용할 수 있다.

### 3.2 2단계: 계정·서버 백업·동기화

- 인증 방식 확정과 고유 닉네임 회원 등록
- 사용자·할 일·반복 규칙·달성 기록용 백엔드
- 앱 삭제·WebView 저장소 초기화 이후 서버 데이터 복원
- 여러 기기 동기화와 오프라인 재전송
- 이용약관, 개인정보처리방침, 탈퇴 및 데이터 삭제

완료 조건: 계정 기반으로 데이터를 안전하게 보존하고 재설치 또는 다른 기기에서 복원할 수 있다.

### 3.3 3단계: 알림 및 사용성 개선

- 할 일과 습관별 알림 설정
- 알림 수신 동의 및 해제 안내
- 알림 딥링크
- 연속 달성일과 주간·월간 달성 통계
- 접근성, 오류 상태, 성능 개선

완료 조건: 알림과 통계가 실제 습관 유지에 도움이 되는지 1~2주간 직접 검증한다.

### 3.4 4단계: 공개 서비스·광고 및 앱인토스 출시

- 운영 로그와 분석 이벤트
- 사업자·정산 정보 등록
- 테스트 및 운영 광고 연동
- 앱인토스 콘솔 등록과 출시 자료 준비
- 샌드박스 및 실제 토스 앱 테스트
- 앱인토스 검수, 출시, 운영 모니터링

완료 조건: 앱이 공개되어 실제 사용자가 이용할 수 있고 광고 수익 지표가 집계된다.

## 4. 기능 요구사항

### 4.1 할 일 관리

- `TODO-001` 사용자는 제목을 입력해 할 일을 생성할 수 있어야 한다.
- `TODO-002` 제목은 필수이며 공백만으로 저장할 수 없어야 한다.
- `TODO-003` 사용자는 할 일의 제목, 메모, 마감 일시, 우선순위를 수정할 수 있어야 한다.
- `TODO-004` 사용자는 할 일을 완료 또는 미완료 상태로 변경할 수 있어야 한다.
- `TODO-005` 완료 시 완료 시각을 기록하고, 미완료로 되돌리면 완료 시각을 제거해야 한다.
- `TODO-006` 사용자는 할 일을 삭제할 수 있어야 하며 삭제 직후 실행 취소 기회를 제공해야 한다.
- `TODO-007` 완료한 항목은 삭제하지 않고 해당 날짜 목록의 미완료 항목 아래로 이동하며, 사용자는 완료를 취소할 수 있어야 한다.
- `TODO-008` 저장 작업 중 중복 제출이 발생하지 않아야 한다.

### 4.2 날짜별 목록과 수동 순서

- `LIST-001` 사용자가 선택한 날짜의 일반 할 일과 반복 습관을 하나의 목록으로 제공해야 한다.
- `LIST-002` Phase 1에서는 오늘·예정·완료 탭이나 별도 필터 UI를 제공하지 않는다.
- `LIST-003` 미완료 항목을 먼저 표시하고 완료 항목을 목록 하단에 표시한다.
- `LIST-004` 데이터가 없을 때 다음 행동을 안내하는 빈 상태를 제공해야 한다.
- `LIST-005` 다른 날짜의 항목은 상단 날짜 선택 또는 캘린더에서 확인한다.
- `LIST-006` 사용자는 드래그 또는 키보드로 날짜별 항목의 수동 순서를 바꿀 수 있어야 하며, 이동 중 항목과 삽입 위치를 시각적으로 확인할 수 있어야 한다. 바꾼 순서는 앱을 다시 실행해도 유지되어야 한다.

### 4.3 반복 습관

- `HABIT-001` 매일, 매주, 특정 요일, 사용자 지정 주기를 지원해야 한다.
- `HABIT-002` 반복 정의는 반복 Todo에 저장하고 날짜별 수행·단일 날짜 수정 기록은 별도 `TodoRecord`로 저장해야 한다.
- `HABIT-003` 날짜별 수행 기록은 완료, 미완료, 건너뜀 상태를 지원해야 한다.
- `HABIT-004` 반복 항목 수정 시 이 날짜만, 이 날짜부터 이후, 전체 반복 중 적용 범위를 선택할 수 있어야 한다. 전체 반복은 첫 occurrence부터 이후 수정으로 처리해 같은 `seriesId`의 과거 분할까지 일관되게 대체해야 한다.
- `HABIT-005` 반복 항목 삭제 시 이 날짜만, 이 날짜부터 이후, 전체 반복 중 적용 범위를 선택할 수 있어야 한다. 전체 반복은 첫 occurrence부터 이후 삭제로 처리해야 한다.
- `HABIT-006` Phase 1은 선택 날짜에서 역산한 연속 달성일을 표시하고, Phase 3에서 주간·월간 달성률과 장기 통계를 제공해야 한다.
- `HABIT-007` 앱을 실행하지 않은 날짜의 기록도 반복 규칙을 기준으로 일관되게 조회되어야 한다.
- `HABIT-008` 자정, 월말, 윤년, 기기 시간대 변경에도 반복 계산이 정확해야 한다.

### 4.4 알림

- `NOTI-001` 사용자는 할 일 또는 반복 습관별로 알림을 켜고 끌 수 있어야 한다.
- `NOTI-002` 알림 날짜, 시간, 반복 요일을 설정할 수 있어야 한다.
- `NOTI-003` 알림 발송 전에 앱인토스 정책에 맞는 수신 동의를 받아야 한다.
- `NOTI-004` 사용자가 수신 동의를 철회하는 방법을 명확히 안내해야 한다.
- `NOTI-005` 알림을 누르면 해당 할 일 또는 습관 화면으로 이동해야 한다.
- `NOTI-006` 완료·삭제·시간 변경 시 기존 예약을 취소하거나 갱신해야 한다.
- `NOTI-007` 동일한 일정에 중복 알림이 발송되지 않아야 한다.
- `NOTI-008` 발송 실패는 기록하고 재시도 가능 여부를 판단해야 한다.

### 4.5 로컬 저장 및 백업

- `DATA-001` 개인 사용 MVP는 IndexedDB에 데이터를 저장해야 한다.
- `DATA-002` 페이지 새로고침과 앱 재실행 후에도 데이터가 유지되어야 한다.
- `DATA-003` 저장 데이터에 스키마 버전을 기록하고 버전별 마이그레이션을 제공해야 한다.
- `DATA-004` 사용자는 데이터를 파일로 내보내고 다시 가져올 수 있어야 한다.
- `DATA-005` 가져오기 전 데이터 형식과 버전을 검증해야 한다.
- `DATA-006` 전체 초기화 전에 명시적인 확인을 받아야 한다.
- `DATA-007` 네트워크가 없어도 할 일과 습관의 핵심 기능을 사용할 수 있어야 한다.

### 4.6 회원 식별 및 서버 동기화

- `SYNC-001` Phase 2 구현 전에 인증·계정 복구 방식을 확정해야 한다.
- `SYNC-002` 닉네임을 사용할 경우 표시 식별자로만 취급하고 인증 수단으로 신뢰하지 않아야 한다.
- `SYNC-003` 서버는 사용자별 데이터 접근을 분리해야 한다.
- `SYNC-004` 첫 회원 등록 시 기존 로컬 데이터를 닉네임 계정 데이터로 이전할 수 있어야 한다.
- `SYNC-005` 오프라인 변경사항을 저장하고 연결 복구 후 서버로 재전송해야 한다.
- `SYNC-006` 여러 기기의 동시 수정 충돌에 일관된 해결 규칙을 적용해야 한다.
- `SYNC-007` 삭제된 항목이 다른 기기에서 다시 생성되지 않도록 삭제 상태를 동기화해야 한다.
- `SYNC-008` 로그아웃 또는 기기 연결 해제 이후 다른 사용자가 이전 사용자의 세션과 데이터에 접근할 수 없어야 한다.
- `SYNC-009` 사용자는 탈퇴와 전체 데이터 삭제를 요청할 수 있어야 한다.
- `SYNC-010` 앱인토스 서버 API 호출에는 mTLS 인증을 적용해야 한다.

### 4.7 인앱 광고

- `AD-001` 개발·검수 환경에서는 테스트 광고 ID만 사용해야 한다.
- `AD-002` 테스트 광고 ID와 운영 광고 ID를 환경 설정으로 분리해야 한다.
- `AD-003` 최초 광고 형식은 목록 하단의 배너 광고를 기본으로 한다.
- `AD-004` 광고 로드 실패 또는 No Fill 상황에서도 핵심 기능과 화면 배치가 깨지지 않아야 한다.
- `AD-005` 광고 요청, 수신, 노출 시도, 노출 성공, 클릭, 실패를 기록해야 한다.
- `AD-006` 광고를 핵심 입력·완료 동작보다 우선해서 노출하지 않아야 한다.
- `AD-007` 할 일 한 건을 완료할 때마다 전면 광고를 노출하지 않아야 한다.
- `AD-008` 전면 광고는 사용자 데이터로 타당성이 확인된 자연스러운 화면 전환 지점에서만 후속 검토한다.
- `AD-009` 앱인토스와 Google AdMob 광고 정책을 준수해야 한다.

### 4.8 분석

- `ANALYTICS-001` 첫 할 일 생성과 완료를 전환 이벤트로 기록해야 한다.
- `ANALYTICS-002` 반복 습관 생성, 달성, 건너뜀을 기록해야 한다.
- `ANALYTICS-003` 알림 동의, 철회, 알림을 통한 진입을 기록해야 한다.
- `ANALYTICS-004` 광고 관련 이벤트와 오류를 기록해야 한다.
- `ANALYTICS-005` 이벤트 이름과 파라미터에 일관된 명명 규칙을 사용해야 한다.
- `ANALYTICS-006` 제목, 메모 등 사용자가 입력한 내용과 개인정보를 분석 이벤트에 포함하지 않아야 한다.
- `ANALYTICS-007` 대표 전환 지표의 초기값은 첫 할 일 완료로 한다.
- `ANALYTICS-008` 활성 지표의 초기값은 첫 방문 7일 후 재방문으로 한다.

## 5. 데이터 모델 요구사항

### 5.1 Todo

- `id`: 고유 식별자
- `type`: `one_time` 또는 `recurring`
- `seriesId`: 분할된 반복 Todo의 계보 식별자, 일반 Todo는 없음
- `revision`: 같은 series 내 반복 정의 버전, 일반 Todo는 없음
- `title`: 제목
- `memo`: 메모
- `status`: 일반 Todo의 미완료 또는 완료, 반복 Todo는 날짜별 `TodoRecord` 사용
- `priority`: 우선순위
- `dueDate`, `dueTime`: 저장 당시의 한국 달력 날짜와 선택 시각
- `completedAt`: 일반 Todo 완료 시각
- `repeatFrequency`, `repeatInterval`, `repeatWeekdays`: 반복 유형·간격·요일
- `repeatStartDate`, `repeatEndDate`: 시작일과 종료일을 포함하는 반복 유효 범위
- `timezone`: Phase 1에서는 `Asia/Seoul` 고정
- `createdAt`, `updatedAt`, `deletedAt`: 변경 추적 시각

`one_time`은 반복 관련 필드와 `seriesId`, `revision`이 없어야 한다. `recurring`은 반복 필드, `seriesId`, `revision`을 가져야 하며 `status`, `completedAt`으로 날짜별 수행 상태를 표현하지 않는다.

### 5.2 TodoRecord

- `id`: 고유 식별자
- `seriesId`: 반복 Todo 계보 식별자
- `targetDate`: 수행 대상 날짜
- `status`: 완료, 미완료 또는 건너뜀
- `completedAt`: 완료 시각
- `overrides`: 이 날짜만 수정한 `title`, `memo`, `priority`, `dueTime`의 선택적 필드 집합
- `hidden`: 이 날짜만 삭제했는지 여부
- `createdAt`, `updatedAt`, `deletedAt`: 변경 추적 시각

같은 `seriesId + targetDate` 조합은 하나만 존재해야 한다. 조회 시 targetDate에 유효한 Todo revision과 결합한다. 이후 날짜부터 수정하면 대상 Todo를 전날 종료하거나 시작일이 같을 때 소프트 삭제하고, 이후 활성 revision을 소프트 삭제한 뒤 `maxRevision + 1`의 새 Todo를 만든다. 대상 날짜 이전 콘텐츠와 TodoRecord는 수정하지 않으며 새 규칙에서 더 이상 발생하지 않는 미래 record만 같은 transaction에서 소프트 삭제한다. 이후 날짜부터 삭제하면 같은 범위의 활성 revision과 TodoRecord를 소프트 삭제한다.

### 5.3 Reminder

- `id`: 고유 식별자
- `todoId` 또는 `seriesId + targetDate`: 알림 대상
- `scheduledAt`: 발송 예정 시각
- `timezone`: 발송 기준 시간대
- `enabled`: 사용 여부
- `deliveryStatus`: 예약, 발송, 실패 또는 취소
- `createdAt`, `updatedAt`: 변경 추적 시각

## 6. UI 및 사용성 요구사항

- `UX-001` 모바일 세로 화면을 우선 지원해야 한다.
- `UX-002` 앱인토스 비게임 내비게이션과 Safe Area를 준수해야 한다.
- `UX-003` 토스 내비게이션의 뒤로가기와 앱 내부 뒤로가기를 중복 노출하지 않아야 한다.
- `UX-004` 최초 화면에서 뒤로가기를 누르면 미니앱이 정상 종료되어야 한다.
- `UX-005` 주요 터치 영역은 오조작을 줄일 수 있는 충분한 크기로 제공해야 한다.
- `UX-006` 색상만으로 완료, 오류, 우선순위를 구분하지 않아야 한다.
- `UX-007` 로딩, 빈 상태, 저장 실패, 네트워크 오류에 대한 피드백을 제공해야 한다.
- `UX-008` 앱 진입 직후 광고나 알림 동의 팝업으로 핵심 화면을 가리지 않아야 한다.
- `UX-009` iframe을 사용하지 않아야 한다.
- `UX-010` 상단 날짜 줄은 처음 열 때 오늘을 가운데에 두고 앞뒤 3일을 표시한다. 양쪽의 이전·다음 버튼은 현재 보이는 7일 묶음을 기준으로 7일 전·후 페이지를 슬라이드 전환하되 선택 날짜는 바꾸지 않는다. 보이는 날짜를 누르면 해당 날짜의 목록만 선택하고 날짜 배치는 이동시키지 않는다. 상단 오늘 버튼은 오늘을 선택하면서 오늘이 가운데인 페이지로 복귀하고, 오늘 칸은 선택 여부와 관계없이 테두리로 구분한다. 날짜 줄 자체에는 드래그 탐색을 적용하지 않는다.
- 목록 제목은 날짜와 관계없이 ‘할 일’, 항목 생성 버튼은 ‘추가’로 표시한다.
- `UX-011` 할 일 생성·수정의 날짜, 시간과 반복 종료일은 한국어 라이브러리 선택 UI를 제공한다. 날짜·시간 문자열 저장 계약과 선택 해제, 키보드 조작을 유지한다.
- `UX-012` 달성 영역 제목은 오늘에는 ‘오늘의 달성’, 다른 날짜에는 ‘M월 D일의 달성’을 사용하고 완료 개수와 다음 행동을 함께 안내한다.
- `UX-013` 새 할 일의 시간과 반복 기본값은 각각 없음과 꺼짐이다. 날짜와 중요도는 같은 줄에 표시하고, 중요도는 낮음·보통·중요 선택 상태를 명확히 보여준다. 입력 폼은 화면 중앙에 독립된 팝업으로 표시하고 모바일에서도 저장 버튼을 화면 안에서 사용할 수 있어야 한다.
- `UX-014` 로그인 기능을 제공하기 전에는 상단 계정 진입 버튼에 개인 이니셜 대신 일반 사용자 아이콘을 표시한다. 이모지 선택지는 별도의 세로 스크롤 없이 한 패널에서 확인할 수 있어야 한다.
- `UX-015` 완료 토글은 별도 하단 토스트를 표시하지 않는다. 완료된 카드는 체크 버튼, 배경, 취소선과 ‘완료됨’ 문구를 함께 사용해 상태를 명확히 전달하고 완료 취소 기능을 유지한다.
- `UX-016` 앱을 처음 실행하면 할 일·날짜와 완료·기기 저장 방식을 설명하는 비차단형 인라인 온보딩 가이드를 표시한다. 가이드는 핵심 목록과 조작을 가리지 않아야 하며, 확인 또는 건너뛰기 뒤에는 자동으로 다시 표시하지 않고 설정에서 다시 열 수 있어야 한다.
- `UX-017` 새 항목 입력 팝업을 열 때 텍스트 입력에 자동 포커스하지 않아 모바일 소프트 키보드를 즉시 표시하지 않는다. 사용자가 입력란을 직접 누르거나 필수값 오류가 발생했을 때만 제목 입력으로 포커스를 이동한다.
- `UX-018` 월간 캘린더는 해당 날짜의 건너뜀을 제외한 일정 달성률을 25%, 50%, 75%, 100% 단계로 시각화하고 범례, 접근성 이름과 100% 완료 표시를 함께 제공해 색상만으로 상태를 전달하지 않는다.

## 7. 비기능 요구사항

### 7.1 성능 및 안정성

- 초기 화면은 일반적인 모바일 네트워크 환경에서 빠르게 상호작용 가능해야 한다.
- 1,000개의 할 일이 있어도 날짜별 목록 생성·정렬과 스크롤이 눈에 띄게 멈추지 않아야 한다.
- 저장 중 앱이 종료되어도 기존 정상 데이터가 손상되지 않아야 한다.
- 광고와 분석 기능의 장애가 할 일 기능의 장애로 이어지지 않아야 한다.

### 7.2 보안 및 개인정보

- 인증 비밀키, mTLS 인증서, 운영 광고 ID를 소스 저장소에 커밋하지 않아야 한다.
- 모든 외부 통신은 HTTPS를 사용해야 한다.
- 서버 API는 인증, 인가, 입력값 검증, 요청 제한을 적용해야 한다.
- 최소한의 개인정보만 수집하고 처리 목적과 보유 기간을 고지해야 한다.
- 로그와 분석 데이터에 할 일 제목, 메모, 인증 토큰을 기록하지 않아야 한다.
- 탈퇴 또는 삭제 요청 완료 후 정책에 따른 기간 내 데이터를 제거해야 한다.

### 7.3 호환성

- 앱인토스가 지원하는 Android와 iOS 토스 앱에서 테스트해야 한다.
- 구현 및 출시 시점의 최신 앱인토스 WebView SDK를 사용해야 한다.
- 광고 분석에 필요한 최소 SDK 버전은 개발 시작 시 최신 공식 문서에서 다시 확인해야 한다.
- 빌드 결과물은 앱인토스의 최신 번들 크기 제한을 충족해야 한다.

- 로컬 데이터 저장, 복원, 마이그레이션

- 앱 스킴과 알림 딥링크 진입
- 토스 내비게이션 및 뒤로가기
- 느린 네트워크와 네트워크 단절
- 큰 글자, 스크린리더, 색상 대비, 터치 영역
- 테스트 광고 로드·노출·실패
- 이용약관, 개인정보처리방침, 탈퇴 경로

## 9. 앱인토스 출시 및 운영 요구사항

- 앱 이름, 영문 식별자, 로고, 설명, 카테고리를 콘솔에 등록해야 한다.
- 이용약관, 개인정보처리방침, 고객센터 연락처를 제공해야 한다.
- 등록한 모든 앱 스킴과 딥링크가 정상 동작해야 한다.
- 앱인토스 비게임 출시 체크리스트를 모두 점검해야 한다.
- 번들은 업로드 시점의 앱인토스 용량 정책을 준수해야 한다.
- 샌드박스에서 기능 검증 후 실제 토스 앱에서 최종 검증해야 한다.
- 운영·기능·디자인·보안 검수 결과의 반려 사유를 수정하고 재검수를 요청해야 한다.
- 광고 수익화를 위해 사업자 정보, 약관 동의, 정산 정보를 등록해야 한다.
- 출시 후 DAU, 7일 재방문, 할 일 완료율, 광고 요청 대비 노출 성공률, eCPM을 모니터링해야 한다.
