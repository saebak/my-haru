# 설계 결정 기록

## 상태 정의

- `확정`: 구현 기준으로 사용한다.
- `제안`: 기본 설계에 반영했으며 사용자 확인이 필요하다.
- `보류`: 현재 단계에서는 구현하지 않는다.
- `동결`: 이전 검토 자료만 보존하며 다시 결정하기 전에는 구현하지 않는다.
- `폐기`: 더 이상 사용하지 않는다.

## Phase 2 시작 전에 재검토할 항목

### ADR-012. 닉네임 서버 보안 경계

1. **Edge Function 경계(권장)**: 브라우저의 업무 테이블 권한을 회수하고 서버가 기기 세션과 `user_id`를 검증한다.
2. 공개 RPC 유지: 구성 요소는 적지만 권한 상승 함수, 함수별 grant, `search_path`, 입력 검증을 모두 지속해서 감사해야 한다.

두 안 모두 현재 동결한다. Phase 2 인증 방식이 확정되면 서버 경계도 함께 재설계한다.

### DEC-007. 닉네임 허용 문자

1. **한글·영문·숫자·밑줄, 공백 없음(권장)**: 표시와 검색이 예측 가능하고 사칭성 유사 닉네임을 일부 줄인다.
2. 모든 유니코드와 내부 공백 허용: 표현은 자유롭지만 보이지 않는 문자, 정규화, 유사 문자 대응이 복잡하다.

공통 권장 규칙은 앞뒤 공백 제거, Unicode NFC 정규화, 2~20자, 영문 대소문자 무관 중복 판정이다.

### Phase 2 또는 운영 단계 전에 결정할 항목

#### DEC-002. 닉네임 변경과 재사용

결정할 항목:

- 닉네임 변경 허용 여부
- 변경 후 이전 닉네임을 다른 사용자가 즉시 사용할 수 있는지
- 탈퇴한 닉네임의 재사용 대기 기간

권장안: 변경 허용, 30일에 1회 제한, 이전·탈퇴 닉네임은 30일 예약 후 재사용.

#### DEC-003. 기기 분실·저장소 초기화 시 복구

선택지:

1. 복구 불가 유지: 가장 단순하지만 기기 데이터 삭제 시 서버 데이터도 다시 접근할 수 없다.
2. **1회용 복구 코드(권장)**: 가입 시 고엔트로피 코드를 한 번 보여주고 서버에는 해시만 저장한다.
3. PIN: 사용은 쉽지만 짧은 PIN은 무차별 대입 방어와 강한 rate limit이 필요하다.
4. 추후 Supabase Auth 또는 토스 로그인: 가장 강한 계정 복구지만 현재 결정과 범위가 달라진다.

#### DEC-004. 소프트 삭제 보존 기간

선택지:

1. 7일: 개인정보 최소 보유에 유리하지만 늦은 기기 동기화에 불리하다.
2. **30일(권장)**: 실행 취소·오프라인 기기·운영 복구의 균형이 좋다.
3. 90일: 복구성은 높지만 저장 비용과 개인정보 보유 부담이 커진다.

탈퇴 요청은 일반 항목 삭제보다 짧거나 즉시 하드 삭제하는 별도 정책을 둘 수 있다.

#### DEC-005. 동기화 충돌 처리

선택지:

1. 마지막 서버 도착 변경 우선: 단순하지만 오프라인에서 오래 편집한 내용이 사라질 수 있다.
2. **version 충돌 감지 + 삭제 우선 + 수동 복구(권장)**: 데이터 보존성이 높지만 충돌 UI가 필요하다.
3. 필드 단위 자동 병합: 일부 충돌을 줄이지만 제목·메모 의미 충돌을 완전히 해결하지 못한다.

다중 기기 복구가 보류된 동안 구현은 늦출 수 있지만 DB의 `version` 필드는 지금 포함하는 것이 좋다.

#### DEC-006. 수행 기록 보존 기간

선택지:

1. **회원 탈퇴 전까지 유지(권장)**: 장기 통계가 정확하고 구현이 단순하다.
2. 2년 이후 월별 집계만 유지: 저장량을 줄이지만 원본 통계 재계산이 불가능하다.
3. 사용자 설정 기간: 유연하지만 MVP 범위를 키운다.
